## 🔗 Детальное описание связей

### 1. **users → verification_codes**

| Характеристика | Значение |
|----------------|----------|
| **Связь** | users.id → verification_codes.user_id |
| **Тип связи** | Один-ко-многим (1:N) |
| **Внешний ключ** | verification_codes.user_id REFERENCES users(id) |
| **ON DELETE** | CASCADE |
| **ON UPDATE** | Не указано (по умолчанию NO ACTION) |
| **NULL разрешен** | Да (DEFAULT NULL) |
| **Описание** | Один пользователь может иметь множество кодов верификации. При удалении пользователя все его коды верификации удаляются автоматически |

**Пример:**
- Пользователь с id=1 может иметь несколько кодов верификации (для регистрации, входа, 2FA)
- При удалении пользователя все его коды удаляются

---

### 2. **users → audit_logs**

| Характеристика | Значение |
|----------------|----------|
| **Связь** | users.id → audit_logs.user_id |
| **Тип связи** | Один-ко-многим (1:N) |
| **Внешний ключ** | audit_logs.user_id REFERENCES users(id) |
| **ON DELETE** | Не указано (по умолчанию NO ACTION) |
| **ON UPDATE** | Не указано (по умолчанию NO ACTION) |
| **NULL разрешен** | Да (DEFAULT NULL) |
| **Описание** | Один пользователь может иметь множество записей в логах аудита. user_id может быть NULL для системных действий. При удалении пользователя логи остаются (для истории аудита) |

**Пример:**
- Пользователь с id=1 может иметь множество записей в audit_logs (LOGIN, LOGOUT, UPDATE_FEEDBACK и т.д.)
- Логи сохраняются даже после удаления пользователя для аудита

---

### 3. **users → user_sessions**

| Характеристика | Значение |
|----------------|----------|
| **Связь** | users.id → user_sessions.user_id |
| **Тип связи** | Один-ко-многим (1:N) |
| **Внешний ключ** | user_sessions.user_id REFERENCES users(id) |
| **ON DELETE** | CASCADE |
| **ON UPDATE** | Не указано (по умолчанию NO ACTION) |
| **NULL разрешен** | Нет (NOT NULL) |
| **Описание** | Один пользователь может иметь множество сессий (текущих и прошлых). При удалении пользователя все его сессии удаляются автоматически |

**Пример:**
- Пользователь с id=1 может иметь несколько активных сессий (с разных устройств)
- При удалении пользователя все его сессии удаляются

---

### 4. **users → user_preferences**

| Характеристика | Значение |
|----------------|----------|
| **Связь** | users.id → user_preferences.user_id |
| **Тип связи** | Один-к-одному (1:1) |
| **Внешний ключ** | user_preferences.user_id REFERENCES users(id) |
| **ON DELETE** | CASCADE |
| **ON UPDATE** | Не указано (по умолчанию NO ACTION) |
| **NULL разрешен** | Нет (NOT NULL) |
| **UNIQUE** | Да (UNIQUE constraint) |
| **Описание** | Один пользователь имеет ровно один набор настроек. При удалении пользователя его настройки удаляются автоматически |

**Пример:**
- Пользователь с id=1 имеет ровно одну запись в user_preferences
- При удалении пользователя его настройки удаляются

**Особенность:** Связь 1:1 обеспечивается через UNIQUE constraint на user_id

### 5. **users → feedback**

| Характеристика | Значение |
|----------------|----------|
| **Связь** | users.id → feedback.user_id |
| **Тип связи** | Один-ко-многим (1:N) |
| **Внешний ключ** | feedback.user_id REFERENCES users(id) |
| **ON DELETE** | SET NULL |
| **ON UPDATE** | Не указано (по умолчанию NO ACTION) |
| **NULL разрешен** | Да (DEFAULT NULL) |
| **Описание** | Один пользователь может отправить множество обратных связей. При удалении пользователя user_id в feedback устанавливается в NULL (обратная связь остается, но становится анонимной) |

**Пример:**
- Пользователь с id=1 может отправить несколько обратных связей
- При удалении пользователя его обратные связи остаются, но user_id становится NULL

**Особенность:** Позволяет сохранять историю обратной связи даже после удаления пользователя

### 6. **users → users_history**

| Характеристика | Значение |
|----------------|----------|
| **Связь** | users.id → users_history.changed_by_user_id |
| **Тип связи** | Один-ко-многим (1:N) |
| **Внешний ключ** | users_history.changed_by_user_id REFERENCES users(id) |
| **ON DELETE** | Не указано (по умолчанию NO ACTION) |
| **ON UPDATE** | Не указано (по умолчанию NO ACTION) |
| **NULL разрешен** | Да (DEFAULT NULL) |
| **Описание** | Один пользователь может выполнить множество изменений других пользователей. changed_by_user_id может быть NULL для системных изменений. История сохраняется даже после удаления пользователя |

**Пример:**
- Администратор с id=2 может изменить множество пользователей
- Каждое изменение записывается в users_history с указанием changed_by_user_id=2
- При удалении администратора его изменения остаются в истории

**Логическая связь:** users_history.user_id также логически связан с users.id, но без внешнего ключа (для сохранения истории удаленных пользователей)

## 🔄 Каскадные операции

### CASCADE (каскадное удаление)

**При удалении пользователя автоматически удаляются:**
1. ✅ Все записи в `verification_codes` (коды верификации)
2. ✅ Все записи в `user_sessions` (сессии)
3. ✅ Запись в `user_preferences` (настройки)

**При удалении пользователя НЕ удаляются:**
- ❌ Записи в `audit_logs` (остаются для аудита)
- ❌ Записи в `feedback` (user_id устанавливается в NULL)
- ❌ Записи в `users_history` (остаются для истории)
- ❌ Записи в `feedback_history` (остаются для истории)

### SET NULL (установка NULL)

**При удалении пользователя:**
- `feedback.user_id` устанавливается в NULL (обратная связь становится анонимной)

## 📊 Типы связей

### Один-к-одному (1:1)
- **users ↔ user_preferences** - один пользователь имеет ровно один набор настроек

### Один-ко-многим (1:N)
- **users → verification_codes** - один пользователь, много кодов
- **users → audit_logs** - один пользователь, много логов
- **users → user_sessions** - один пользователь, много сессий
- **users → feedback** - один пользователь, много обратных связей
- **users → users_history** - один пользователь может изменить много других пользователей
- **users → feedback_history** - один пользователь может изменить много обратных связей

## 🛡️ Целостность данных

### Референсная целостность

**Обеспечивается через:**
- Внешние ключи (FOREIGN KEY constraints)
- Правила ON DELETE и ON UPDATE
- UNIQUE constraints для связей 1:1

### Ограничения целостности

1. **Нельзя удалить пользователя, если:**
   - Есть активные сессии (но они удалятся автоматически через CASCADE)
   - Есть настройки (но они удалятся автоматически через CASCADE)

2. **Можно удалить пользователя, даже если:**
   - Есть логи аудита (остаются для истории)
   - Есть обратная связь (user_id становится NULL)
   - Есть история изменений (остается для аудита)

3. **Нельзя создать обратную связь с несуществующим пользователем:**
   - FOREIGN KEY проверяет существование user_id в users

## 🔄 Триггерные связи

### Триггер: trigger_users_history

**Связывает:** `users` → `users_history`

**Механизм:**
- Автоматически создает запись в `users_history` при любом изменении в `users`
- Записывает старое и новое значение в формате JSONB
- Определяет пользователя, выполнившего изменение, через `app.current_user_id`

**Операции:**
- INSERT → записывает new_value
- UPDATE → записывает old_value и new_value
- DELETE → записывает old_value

---

### Триггер: trigger_feedback_history

**Связывает:** `feedback` → `feedback_history`

**Механизм:**

- Записывает старое и новое значение в формате JSONB
- Определяет пользователя, выполнившего изменение, через `app.current_user_id`

**Операции:**
- INSERT → записывает new_value
- UPDATE → записывает old_value и new_value

## 📈 Примеры запросов с JOIN

### Получение пользователя с его настройками (1:1)

```sql
SELECT u.*, up.language, up.notifications_enabled
FROM users u
LEFT JOIN user_preferences up ON u.id = up.user_id
WHERE u.id = 1;
```

### Получение пользователя со всеми его сессиями (1:N)

```sql
SELECT u.username, s.session_token, s.created_at, s.is_active
FROM users u
LEFT JOIN user_sessions s ON u.id = s.user_id
WHERE u.id = 1
ORDER BY s.created_at DESC;
```

### Получение обратной связи с информацией о пользователе (1:N)

```sql
SELECT f.*, u.username, u.display_name, u.email
FROM feedback f
LEFT JOIN users u ON f.user_id = u.id
WHERE f.status = 'new';
```

### Получение истории изменений пользователя (1:N)

```sql
SELECT uh.*, u_changed.username as changed_by_username
FROM users_history uh
LEFT JOIN users u_changed ON uh.changed_by_user_id = u_changed.id
WHERE uh.user_id = 1
ORDER BY uh.operation_date DESC;
```

### Получение статистики пользователя (агрегация через JOIN)

```sql
SELECT 
    u.id,
    u.username,
    COUNT(DISTINCT s.id) as total_sessions,
    COUNT(DISTINCT f.id) as total_feedback,
    COUNT(DISTINCT al.id) as total_logs
FROM users u
LEFT JOIN user_sessions s ON u.id = s.user_id
LEFT JOIN feedback f ON u.id = f.user_id
LEFT JOIN audit_logs al ON u.id = al.user_id
WHERE u.id = 1
GROUP BY u.id, u.username;
```

## ⚠️ Важные замечания

1. **CASCADE удаление:**
   - При удалении пользователя автоматически удаляются связанные данные в verification_codes, user_sessions, user_preferences
   - Это предотвращает "висячие" ссылки

2. **SET NULL для feedback:**
   - Обратная связь сохраняется даже после удаления пользователя
   - Это позволяет сохранить историю обратной связи

3. **История изменений:**
   - users_history и feedback_history не имеют строгих внешних ключей
   - Это позволяет сохранить историю даже после удаления исходных записей

4. **UNIQUE для user_preferences:**
   - Гарантирует, что у каждого пользователя только один набор настроек
   - Обеспечивает связь 1:1
