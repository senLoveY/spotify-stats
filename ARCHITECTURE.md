# Архитектура приложения Spotify Analytics

## 📐 Общая архитектура

Приложение построено на архитектурном паттерне **MVC (Model-View-Controller)** с использованием фреймворка Flask. Система использует гибридную архитектуру с разделением на операционную базу данных (PostgreSQL) и аналитическое хранилище (Snowflake).

## 🛠️ Технологический стек

### Backend
- **Python 3.7+** - основной язык программирования
- **Flask** - веб-фреймворк
- **Jinja2** - шаблонизатор
- **Werkzeug** - утилиты для работы с WSGI

### Базы данных
- **PostgreSQL 15** - операционная база данных (пользователи, сессии, логи)
- **Snowflake** - облачное аналитическое хранилище (треки, артисты, история прослушиваний)

### Внешние сервисы
- **Spotify Web API** - источник музыкальных данных
- **SMTP Server** - отправка email (2FA, отчеты, уведомления)

### Библиотеки и инструменты
- **psycopg2** - драйвер PostgreSQL
- **snowflake-connector-python** - драйвер Snowflake
- **requests** - HTTP клиент для API запросов
- **matplotlib** - генерация графиков
- **openpyxl** - работа с Excel файлами
- **python-dotenv** - управление переменными окружения

### Инфраструктура
- **Docker** - контейнеризация (PostgreSQL, pgAdmin)
- **Docker Compose** - оркестрация контейнеров

## 🎯 Компоненты приложения

### 1. **Слой представления (View Layer)**

**Файлы:** `templates/*.html`

**Ответственность:**
- Отображение пользовательского интерфейса
- Рендеринг шаблонов Jinja2
- Обработка пользовательского ввода через формы

**Основные шаблоны:**
- `base.html` - базовый шаблон с навигацией
- `dashboard.html` - дашборд с графиками и статистикой
- `admin.html` - административная панель

---

### 2. **Слой контроллера (Controller Layer)**

**Файл:** `app.py` (маршруты `@app.route`)

**Ответственность:**
- Обработка HTTP запросов
- Координация между моделью и представлением
- Валидация входных данных
- Управление сессиями

**Основные маршруты:**

| Маршрут | Метод | Описание | Доступ |
|---------|-------|----------|--------|
| `/` | GET | Главная страница | Публичный |
| `/register` | GET, POST | Регистрация пользователя | Публичный |
| `/login-local` | GET, POST | Вход по паролю | Публичный |
| `/login-spotify` | GET | OAuth авторизация Spotify | Публичный |
| `/callback` | GET | OAuth callback | Публичный |
| `/verify-code` | GET, POST | Верификация 2FA | Аутентифицированный |
| `/dashboard` | GET | Дашборд пользователя | Аутентифицированный |
| `/profile` | GET, POST | Профиль пользователя | Аутентифицированный |
| `/recommendations` | GET | Рекомендации артистов | Аутентифицированный |
| `/feedback` | GET, POST | Форма обратной связи | Аутентифицированный |
| `/admin` | GET | Админ-панель | Администратор |
| `/admin/export/excel` | GET | Экспорт данных в Excel | Администратор |
| `/logout` | GET | Выход из системы | Аутентифицированный |

### 3. **Слой модели (Model Layer)**

**Файл:** `app.py` (функции работы с БД)

#### 3.1 PostgreSQL модели

**Функции работы с пользователями:**
- `get_user_by_id()` - получение пользователя по ID
- `get_user_by_username()` - получение по логину
- `get_user_by_spotify_id()` - получение по Spotify ID
- `create_local_user()` - создание пользователя
- `get_all_users()` - получение всех пользователей (с фильтрацией)

**Функции работы с сессиями:**
- `create_user_session()` - создание сессии
- `deactivate_user_session()` - деактивация сессии
- `get_user_sessions()` - получение сессий пользователя

**Функции работы с обратной связью:**
- `create_feedback()` - создание feedback
- `get_feedback_by_id()` - получение по ID
- `get_all_feedback()` - получение всех (с фильтрацией)

**Функции аудита:**
- `log_action()` - логирование действий
- `get_recent_logs()` - получение логов

#### 3.2 Snowflake модели

**Функции работы с треками:**
- `save_tracks_to_snowflake()` - сохранение истории прослушиваний
- `save_tracks_to_snowflake_background()` - асинхронное сохранение

**Функции аналитики:**
- `get_top_tracks_from_snowflake()` - топ треков пользователя
- `get_genre_distribution_from_snowflake()` - распределение по жанрам
- `get_listening_activity_by_hour_from_snowflake()` - активность по часам
- `get_listening_activity_by_weekday_from_snowflake()` - активность по дням

## 🔄 Потоки данных

### Поток 1: Регистрация пользователя

```
Пользователь → /register (POST)
    ↓
Валидация данных
    ↓
create_local_user() → PostgreSQL (INSERT users)
    ↓
generate_verification_code()
    ↓
save_verification_code() → PostgreSQL (INSERT verification_codes)
    ↓
send_verification_email() → SMTP Server
    ↓
Перенаправление на /verify-code
    ↓
Пользователь вводит код
    ↓
verify_code() → PostgreSQL (UPDATE verification_codes, users)
    ↓
Создание сессии → PostgreSQL (INSERT user_sessions)
    ↓
Перенаправление на /dashboard
```

### Поток 2: Авторизация через Spotify

```
Пользователь → /login-spotify
    ↓
Перенаправление на Spotify OAuth
    ↓
Spotify → /callback (с кодом)
    ↓
Обмен кода на токен → Spotify API
    ↓
Получение данных пользователя Spotify → Spotify API
    ↓
Проверка/создание пользователя → PostgreSQL
    ↓
Создание сессии → PostgreSQL
    ↓
Получение истории прослушиваний → Spotify API
    ↓
save_tracks_to_snowflake_background() → Snowflake (асинхронно)
    ↓
Перенаправление на /dashboard
```

### Поток 3: Отображение дашборда

```
Пользователь → /dashboard
    ↓
Проверка аутентификации
    ↓
Получение данных из Spotify API (если нужно обновить)
    ↓
Параллельные запросы к Snowflake:
    ├─→ get_top_tracks_from_snowflake()
    ├─→ get_genre_distribution_from_snowflake()
    ├─→ get_listening_activity_by_hour_from_snowflake()
    └─→ get_listening_activity_by_weekday_from_snowflake()
    ↓
Генерация графиков (matplotlib)
    ↓
generate_user_vibe() → анализ жанров
    ↓
Рендеринг dashboard.html
    ↓
Отправка HTML клиенту
```

### Поток 4: Сохранение данных в Snowflake

```
Данные из Spotify API (история прослушиваний)
    ↓
save_tracks_to_snowflake_background() (в отдельном потоке)
    ↓
Для каждого трека:
    ├─→ MERGE INTO TRACKS (upsert)
    ├─→ Получение жанра артиста → Spotify API
    └─→ INSERT INTO LISTENING_HISTORY (если уникально)
    ↓
Коммит транзакции
```

## 🔐 Система безопасности

### Аутентификация

1. **Локальная аутентификация:**
   - Username/Password
   - Хеширование паролей (Werkzeug bcrypt)
   - Двухфакторная аутентификация через email (2FA)

2. **OAuth 2.0 (Spotify):**
   - Authorization Code Flow
   - Хранение access_token в сессии
   - Автоматическое обновление токенов

3. **Управление сессиями:**
   - Flask sessions (server-side)
   - Хранение сессий в PostgreSQL (user_sessions)
   - Время жизни сессии: 1 час
   - Отслеживание IP адресов и User Agent

### Авторизация

1. **Роли пользователей:**
   - `user` - обычный пользователь
   - `admin` - администратор

2. **Декораторы доступа:**
   - `@admin_required` - проверка роли администратора

3. **Блокировка пользователей:**
   - Флаг `is_blocked` в таблице users
   - Проверка при каждой аутентификации

### Аудит и логирование

- Все действия логируются в `audit_logs`
- История изменений в `users_history` и `feedback_history`
- Триггеры PostgreSQL для автоматического логирования
- Отслеживание пользователя через `app.current_user_id`

## 🎨 Архитектурные паттерны

### Использованные паттерны:

1. **MVC (Model-View-Controller):**
   - Модели: функции работы с БД
   - Представления: HTML шаблоны
   - Контроллеры: Flask маршруты

2. **Repository Pattern:**
   - Функции работы с БД инкапсулируют доступ к данным
   - Разделение логики доступа к PostgreSQL и Snowflake

3. **Decorator Pattern:**
   - `@admin_required` для контроля доступа
   - `@app.before_request` для предобработки запросов

4. **Template Method:**
   - Базовый шаблон `base.html` с расширениями

5. **Background Processing:**
   - Асинхронная обработка через threads

## 📈 Масштабируемость

### Текущие ограничения:

1. **Синхронная обработка запросов:**
   - Flask в режиме разработки (single-threaded)
   - Для production рекомендуется Gunicorn/uWSGI

2. **Фоновые задачи:**
   - Использование threads (ограничено GIL)
   - Для production рекомендуется Celery/RQ

3. **База данных:**
   - PostgreSQL - вертикальное масштабирование
   - Snowflake - автоматическое масштабирование

### Рекомендации по масштабированию:

1. **Production сервер:**
   - Использовать Gunicorn с несколькими workers
   - Настроить reverse proxy (Nginx)

2. **Очереди задач:**
   - Интеграция Celery для фоновых задач
   - Redis/RabbitMQ как брокер сообщений

3. **Кэширование:**
   - Redis для кэширования данных
   - Кэширование результатов аналитики

4. **Мониторинг:**
   - Логирование (ELK stack)
   - Метрики (Prometheus/Grafana)
   - APM (Application Performance Monitoring)

## 📝 Примечания по архитектуре

1. **Монолитная структура:**
   - Все в одном файле `app.py` (для простоты)
   - Для больших проектов рекомендуется разделение на модули

2. **Смешанные роли БД:**
   - PostgreSQL для операционных данных
   - Snowflake для аналитики
   - Разделение позволяет оптимизировать каждую БД под свою задачу

3. **Внешние зависимости:**
   - Spotify API - источник данных
   - SMTP - отправка email
   - Все внешние сервисы имеют fallback обработку ошибок

4. **Безопасность:**
   - Пароли хешируются (bcrypt)
   - 2FA для дополнительной защиты
   - Проверка прав доступа на уровне маршрутов
